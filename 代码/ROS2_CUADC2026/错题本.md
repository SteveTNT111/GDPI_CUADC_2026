# CUADC ROS1→ROS2 翻译项目 — 错题本（每次工作前必看）

> 创建：2026-09-22。教训来源：A1~A3/B1 翻译与仿真验证中**"自己验证通过、用户实机观看时却出问题"**的全部根因与对策。
> 铁律：**用户说"质量优先于速度"** —— 每翻译一个脚本必须自己先跑通，再让用户看；给用户看之前先过一遍下面的清单。

## 0. 每次工作前必看（PRE-FLIGHT 自检清单）

给用户演示/验证任何东西之前，**必须**逐项确认，不能只凭"刚才验证过"：

0. **先跑自动化体检再人工复核**：`bash ~/ROS2_CUADC2026/scripts/preflight.sh`（秒级出 PASS/FAIL 表，覆盖下面 1-3/7 项）→ 有 FAIL 就 `bash ~/ROS2_CUADC2026/scripts/demo_up.sh`（幂等修复+流闸门+摆位+守护）→ READY 后再人工过 1-7（详见 #17）。
1. **进程都在**：`gz sim -s`、`arducopter`（SITL）、`mavros_node`、`sitl_rc_center.py`、GUI `gz sim -g` 全活着。
   - 查 SITL 用 `pgrep -af "sitl/bin/arducopter"` 或 `ss -tln | grep 5760`（`pgrep -x arducopter` 也可，comm=arducopter 已实测）；**SITL/MAVROS 必须 `setsid` 启动**（start_sitl.sh 已内置；否则死在启动命令结束瞬间，见 #16 向量a）；优先用 `scripts/sitl_tee.sh`（时间戳+`SITL_EXIT rc=` 捕获）；**活过 ~130s 窗口后才算稳**（间歇崩溃向量b，见 #1/#16）。
2. **链路用流实据判定**：`ros2 topic hz /mavros/local_position/pose` 有 ~10Hz 频率才算链路活。**禁止**用 `/mavros/state` 的 connected/时间戳/armed 判定 —— transient_local 下 `ros2 topic echo --once` 返回的是**缓存最旧样本**（实测拿到 224s 前 `armed:true` 的假现值），断链后 connected 还会冻结 true（见 #16 向量c）。
3. **关键话题有流**：`ros2 topic hz /mavros/local_position/pose`、相机话题有频率输出。
4. **sourcing 顺序**：`source /opt/ros/humble/setup.bash` **再** `source ~/ROS2_CUADC2026/install/setup.bash`。
   - 工作区 setup 链上 `ros2_gz_ws` 那段会报 `not found: ...ros_gz_sim/local_setup.bash`（那是索引不完整的历史残留），**不致命**，但别再指望 ROS2 里有 ros_gz_bridge。
5. **日志落盘**：`ros2 run ... 2>&1 | tee /tmp/opencode/xx.log`，不要裸管道接 `tail`（timeout 杀管道时缓冲全丢，什么都看不到，误判为卡死/失败 —— 错题 #4）。
6. **演示前 30 秒内重新确认**，不要用 10 分钟前的状态当依据（SITL 会在启动窗口内死，见错题 #1）。
7. **演示窗口真可见**：用 `xprop -root _NET_CLIENT_LIST` 逐个查 `_NET_WM_NAME` + `xwininfo -id`（Map State=IsViewable）确认 Gazebo/相机窗口在**受管列表**里 —— **禁止只用 `xwininfo -root -children` 判定**（被 Mutter 托管的窗口会从该列表消失，见错题 #15）。演示用相机窗口一律 `GDK_BACKEND=x11` 启动（Wayland 窗口 X 侧不可见、不可摆位）。
8. **节点"卡死且 0 ERROR"→ 先 `head -25` 日志找 `Exception in thread`**：回调异常从 `executor.spin()` 顶层冒出，只在**日志首屏**留一条 Traceback，随后所有回调停摆、主线程干等数据、**一条 [ERROR] 都不产生**（错题 #19）。别只 grep [ERROR] 就下"没病"结论。
9. **新脚本执行位**：write 工具建的文件默认 **644** —— `python3 文件` 直跑不暴露，`launch`/`ros2 run` 才炸：报 `executable 'X' not found on the libexec directory`（**文件明明在**，报错文案有误导性，实为不可执行）。新建/重写将被 launch 执行的脚本后 `ls -l` 确认 +x（symlink 安装权限跟随源文件），见 #20。

## 1. 错题表

### #1 SITL 启动间歇静默崩溃（时序竞态）⚠️ 最常背锅
- **现象**：重启仿真后 ~60-90s 内 arducopter 无声死亡（无 core、无日志、5760 消失），MAVROS 疯狂报 `tcpXX: send: channel closed`。有时又在首帧 JSON 后立刻死。
- **根因**：现有 lock_step 修复（模型 SDF `<lock_step>0</lock_step>`）消除了主要崩溃，但**仍残留一个启动窗口内的时序竞态**（gdb/降速下不复发 → 纯 timing 问题）。
- **对策**：SITL 用工具"后台任务"方式拉起后，**盯 90s 危险窗口**再继续；存活即长期稳定。死了就再拉起一次（通常 1-2 次内成功）。不要在演示前才重启整套环境。
- **状态（2026-09-23 修正定案）**：原判"启动窗口竞态"只覆盖部分现象 —— C1 验证前夜连死 4 次后拆出**三个互相独立的向量**（进程组回收 / 间歇内生崩溃 / state 缓存假象），完整定案见 **#16**。其中：向量(a) 已用 `setsid` 修复并实证；向量(c) 已改用流实据判定；**向量(b) 间歇内生崩溃仍挂起** —— 同参数下 #6 满血存活 300s+，证实"**活过 ~130s 窗口的实例确实长期稳定**"，复发时用 `scripts/sitl_tee.sh` 的 `SITL_EXIT rc=`（137/139/143）直接定罪。

### #2 MAVLink 数据流不会自动推
- **现象**：MAVROS `connected: true` 但 `local_position/pose` 等全部零流量。
- **根因**：SITL 的 `SR0_*`（sitl_streams.parm）只是**速率门控**，不是请求；没请求就一条不推。
- **对策**：链路健康时跑 `python3 scripts/request_streams.py`（8/8 成功即好）。**先确认 SITL 活着再跑** —— 死了跑必失败 0/8，还会让 MAVROS 日志刷 channel closed，误导排查。
- **状态**：已确认。

### #3 我的验证 vs 用户观看时"出问题"
- **现象**：A3 我验证通过后，用户来看时屏幕没反应 —— 因为**演示环境在两次验证之间崩了/被清了**（SITL 死、进程被 pkill、话题没流）。
- **根因**：验证是一次性事件，环境是持续的；两件事之间没有"保活"机制。
- **对策**：见 PRE-FLIGHT 清单 —— **演示前 30s 内全链路复查**。禁用"刚才还好好的"心态。
- **状态**：流程已定，执行靠自觉。

### #4 timeout + 管道吞日志
- **现象**：`timeout 90 ros2 run ... 2>&1 | grep ... | tail` 超时被杀，**一行输出都看不到**，无法判断节点是在跑还是卡死。
- **根因**：管道缓冲 + kill 不 flush。
- **对策**：`tee /tmp/opencode/xx.log` 落盘后再过滤；或用后台任务方式跑节点，从输出文件读。
- **状态**：已确认。

### #5 ros2 run 被杀、子进程成孤儿
- **现象**：`timeout` 杀管道，但 `ros2 run` 的 Python 子进程变成孤儿**继续跑**（控制着飞机）。
- **后果**：好的一面——A3 演示时靠它救场（飞机继续完成了起飞）；坏的一面——会留下僵尸节点重复干扰话题。
- **对策**：每次跑完节点检查 `pgrep -af one_key_takeoff|camera_node|detector_node` 清残留；集群环境任务脚本退出不保证杀子树。
- **状态**：已确认。

### #6 rclpy `uint8[]` 字段直接赋 bytes 巨慢（92KB 图像 ≈ 52ms/帧）
- **现象**：B1 图像发布率只有 ~8Hz，CPU 明显卡。
- **根因**：rclpy 对 `uint8[]` 逐元素转换。
- **对策**：赋 `array.array('B', arr.tobytes())`（≈0ms，发布率 8→17Hz）。**B2 的 `_make_img_msg` 同样处理**。
- **状态**：已修复并记录在 B1。

### #7 ROS2 消息字段差异
- CameraInfo：字段**小写** `d/k/r/p`（ROS1 大写 `D/K/R/P`）。
- `geometry_msgs/TransformStamped` 的变换用 `tf2` API（`buffer.lookup_transform`）。
- 图像 msg 的 `step` 要用 `arr.strides[0]`（原 ROS1 版忽略通道数会错）。
- **状态**：B1 已踩已修。

### #8 ROS2 日志/打印兼容
- `logger.info("fmt %s", arg)`（printf 式多参）在 rclpy 会抛 `TypeError` → 必须 `"fmt %s" % arg`。
- `rospy.get_param("~x")` → `declare_parameter("x")`，参数名去 `~`。
- `rospy.Rate.sleep()` 会处理回调，rclpy 的 `rate.sleep()` **不处理** → 后台 `MultiThreadedExecutor.spin()` 线程驱动。
- **状态**：A3 已踩已修。

### #9 DDS 发现异步竞态
- **现象**：新建节点后立刻 `count_publishers("/mavros/state")` 返回 0 → 误判 MAVROS 没跑，重复启动两个 MAVROS 抢 5760 → 连接超时。
- **对策**：`mavros_discovery_grace`（默认 3s）宽限窗口后再判定。
- **状态**：A3 已修复。

### #10 GZ CLI 输出噪声
- `gz model --list` / `gz topic` 输出会埋在一堆 `gz_frame_id` SDF 警告里，还带颜色转义码。
- **对策**：先 `sed 's/\x1b\[[0-9;]*m//g'` 去色，再 grep 具体字段；位姿用 `/world/.../dynamic_pose/info`。
- **状态**：已确认。

### #11 GUI 显示
- GUI 必须 `gz sim -g` 另开（server 是 `-s` headless）。DISPLAY=:0 可用 → 用户能看屏幕。
- 用户要看"效果"（画面/图像）时：确认 GUI 进程活着 + 对应话题（相机/检测标注图）有数据，而不是只看话题数值。
- **状态**：已确认。

### #12 MAVROS ROS2 的 ENU 约定（最终根因，2026-09-22 验证定案）
- **现象链**：
  1. 最初按 ROS1 思维写成 NED：`setpoint_position/local` 发 `(0, 32.5, -3)`，飞机 60s 只挪 11.6m 就**头朝下栽到地面**（z=0.03、姿态 180° 翻转 → 只能重启整套仿真）。
  2. 一度以为是 `frame_id` 问题（`base_link` vs `map`），把 frame_id 换成 "map"。
  3. **最终验证**：拆机逐话题对照 —— MAVROS ROS2 的 `setpoint_position/local` 入站**与** `local_position/pose` 出站**均为 ENU**（x=east, y=north, z=up），与 MAVROS ROS1（NED）相反。
- **根因**：MAVROS ROS2 内置 `tf2_ros` 把 `/mavros/local_position`（NED）转成 `map`/`base_link`（ENU）再对外发布/接收；ROS1 版直接透传 NED。翻译时**不能照抄 ROS1 的坐标符号**。
- **对策**：ROS2 侧全部用 ENU 目标：`publish_local_target(x=east, y=north, z=up)`（10Hz）。起飞点已离地 >1.5m 时跳过 TAKEOFF 服务。
- **铁律**：跨 ROS 版本翻译坐标类代码时，先验证目标框架本身坐标约定（topic echo + 几何交叉核对），再写逻辑。
- **状态**：已定案。`competition_mission_common.py::make_local_pose / publish_local_target`（520/530 行附近）即 ENU。完整飞行验证：GUIDED→ARM→TAKEOFF→ 平飞 E=32.51 N=0.00 z=2.99 → CONDITION_YAW 90° → LOITER 收尾。

### #13 pymavlink 5762 无数据流 + arm 读取陷阱（弃用）
- **现象**：5740（console）可用；5762 连上后**无数据流**（流 0/0，`pymavlink` 收不到任何消息）；`arm()` 后立刻读 attribute 常为旧值。
- **根因**：5762 是 MAVLink2 的**非标准备用通道**，SITL 不默认向它推流；arm 是**异步指令**，服务端确认要等应答循环，属性不会即时更新。
- **对策**：**弃用 pymavlink 直连**（5760 已被 MAVROS 独占）。MAVROS 的 arming 服务（`/mavros/cmd/arming`）才是可靠通道。
- **状态**：已弃用；脚本保留未使用。

### #14 相机姿态/检测的几何与接口坑（B2，2026-09-22）
> **状态更新（2026-09-30）**：仿真相机已由「前下 45°」改为「CG 正下方、镜头朝下（pitch=+90°）」——
> 与 detector/瞄准的正下假设、真机 D435i 语义一致；悬停实测图像顶部=机头、右侧=右舷（见验证记录）。
> 遗留：`camera_mount_z`（仿真实际 0.12m，detector 默认 0.40）、`invert_camera_x`（镜像方向）与 launch 里的
> static TF（z=+0.4/yaw=90°，与正下安装不符）需 T4 用真实相机链标定。

- **相机朝下 pitch 符号**：绕机体系 Y 正转 = 朝前下 → SDF `camera_link` pose 用 **pitch=+0.7854**（`0.12 0 0.02 0 0.7853981633974483 0`）。误用 -0.7854 会朝天 → 有效深度 0%。
- **俯视视角 vs 悬停点**：3m 高、pitch 45° 时地面视野仅从机身下 ~1m 到前方 ~9.5m、水平半角 34.7° —— 悬停在投放区正上方时三个圆筒（散布 ±1m）几乎全在 FOV 外（筒2 方位角 38.7° > 34.7°）。**验证前先算视野几何**，或先 probe_depth 核对。
- **stub 深度突起分割的 blur 窗口**：筒在像面约 20~36px，blur 窗口必须**大于**目标像尺寸（ksize=21 时 3 个筒干净检出；ksize=5~9 时只有边缘一圈 gap>阈值 → 稀疏点被 MORPH_OPEN 全灭 → 0 目标）。腐蚀也要轻（erode_k=1）。
- **`_FakeTensor(np.ndarray 子类) 索引返回标量`**：`box.xyxy[0].detach().cpu().numpy()` 对 `_FakeTensor` 会炸 —— ndarray 子类 `[0]` 返回 numpy 标量（无 `.detach`）；而 ultralytics 的 `(1,4)` torch 张量 `[0]` 返回 `(4,)` 张量。改为统一 `_to_numpy()`（detach→cpu→numpy→np.asarray，ndim>1 取首行、arr.reshape(-1) 后取 [0]）兼容两条路径。
- **相机外参 vs detector 假设不一致**：`transform_camera_to_body` 是 ROS1 原样的**正下安装**数学（真机 D435i 语义，`X_body=-Y_cam`）；仿真相机是前下 45°。两者外参不同 → 桩模式下 detector 输出的 body/ENU 数值与仿真几何有系统偏差，但**检测/深度/相机系坐标/反投影不受影响**（已用真实外参做双向几何交叉验证，误差 <0.1m）。仿真要验证 body/ENU 需外参一致。
- **状态**：已修复，B2 验证 3/3 目标 position_valid 通过；`verify_b2_geo.py` 双向几何校验误差 0.06~0.10m。

### #15 Gazebo GUI "黑屏不显示"双重误诊（2026-09-22 深夜，定案）
- **现象**：整晚判定"Qt 窗口 1x1 IsUnMapped 永不显示、外部强制 map 后黑屏、主线程 futex 死锁"，围绕 `Gazebo GUI`（1x1 诱饵窗）排查数小时（strace/gdb/渲染循环变体/截屏 portal 全上）。
- **根因（两条检测错误叠加）**：
  1. **看错了窗口**：`xwininfo -root -children` 只列 root 直系子窗口，**被 Mutter 托管（reparent 进 frame）的窗口会从该列表消失**。真主窗口 `Gazebo Sim`（1000×845、IsViewable、完整渲染赛场+无人机）一直在 `_NET_CLIENT_LIST` 里好好显示着；盯的 `Gazebo GUI` 1x1 是从未 map 的辅助诱饵窗 → 对它采样当然全黑。
  2. **把正常等待当死锁**：gdb 瞬间抓到主线程 `RenderSync::WaitForWorkerThread` 是**每帧正常等待**；健康态 wchan 是 `do_poll`。65 线程进程随手抓 futex 必然命中等待态。Qt 在本 Xwayland 上完全正常（最小 Qt5 程序 40ms 即被 Mutter 接管）。
- **正确检测/验证方法（铁律）**：
  - 窗口在不在 → `xprop -root _NET_CLIENT_LIST` + `xwininfo -id <ID>`（Map State/几何/parent）。
  - GUI 活不活 → ① 主线程 `/proc/PID/task/PID/wchan` 常态应为 `do_poll`；② **对外部操作做像素 ROI 差分**：`gz service /world/<w>/control pause:true` 往返 → 左下暂停按钮 ROI 变化 1.64% = 实时响应实证。
  - 自制 `/tmp/opencode/xsnap`（只读 XGetImage→PPM）→ cv2 转 PNG → 直接 `read` 亲眼核对画面内容。
- **附带教训**：
  - **杀进程铁律**：`killall -9 ruby` 杀 gz server（comm=ruby）；`pkill -f` / awk 匹配含 `gz sim -g`、`bash -c` 字样的命令会杀掉**自己所在的 shell**（现象=命令秒退"无输出"）→ awk 必须 `!/bash -c/ && !/awk/`，一律按 pid 精确 kill。
  - server 死 → `createGui` 死等 `/gazebo/worlds` → 窗口永不出（先体检 server 再开 GUI）。
  - **gz CLI（本版本）**：发布用 `-p 'field: val'`（**没有 `-k`**）；`/world/<w>/control` 走 **service**（`--reqtype gz.msgs.WorldControl --reptype gz.msgs.Boolean --req 'pause: true'`）；`gz model -l` 的 `-l` 是 --link（列表用 `--list`），且只能打印位姿不能设置。
  - **Wayland 窗口**（`GDK_BACKEND=wayland`，cv2/GTK 默认）X 侧完全不可见 → 演示窗口一律 `GDK_BACKEND=x11`（Xwayland 正常显示 + 可验证/摆位/置顶）。
  - GNOME Screenshot portal 无对话框 60s 超时 → 本环境无截屏手段；验证只能靠 X 抓帧 + **用户亲眼确认**。
  - gdb：`-batch -ex run -ex bt…` + sleep 后 `kill -INT <gdb_pid>`（`-ex interrupt` 无效）；`thread apply all bt 3` 太浅看不到 worker 业务帧 → 至少 bt 15。
- **状态**：已定案；双窗口（Gazebo Sim 赛场 + B1 相机）用户亲眼确认"两个都看到了，画面正常"。

### #16 SITL 连环死亡三向量定案 + 链路假象（2026-09-23 凌晨，C1 验证前夜）
- **背景**：C1 验证前 SITL 连死 4 次（#1 遗留现象集中爆发），逐次取证后确认是**三个互相独立的向量**叠在一起误判。单看任何一个都解释不了全部现场。
- **向量 (a) — 启动命令结束时的进程组回收（已修复）**：harness 在前台命令退出时对**命令进程组**发信号清场；只用 `nohup`（不换会话）的 SITL 死在"启动它的命令结束瞬间"。取证：日志打印 `Exitting`（只有 ArduPilot 的 SIGTERM 处理器才会打这行）+ 外层 wrapper 未来得及写退出码。**对策：一律 `setsid`**（start_sitl.sh 已改）。实证：setsid 的 MAVROS（248702/263246）与 SITL 包装器（#6）全部活过命令结束；未 setsid 的 #3 当场 Exitting。

### #29 rclpy C 层 SIGINT 在信号上下文 rcl_shutdown 与主线程收尾真并行 → FastDDS `std::terminate`（rc=-6）——两半修：掩码定向 + Python 级处理器（2026-09-24，E3 RUN C rc=-6 实据，五条件矩阵定案）

### #44 `ros2 topic pub --once` 无订阅者时阻塞等待 → HTTP 请求挂死（2026-09-30，Web UI 舵机按钮）
- **现象**：Web UI 后端用 `ros2 topic pub --once /servo/cmd std_msgs/String "{data: 'all off'}"` 发舵机指令；
  `servo_test.py` 未运行时该命令**不返回**——终端一直打印 `Waiting for at least 1 matching subscription(s)...`，
  直到 15s 超时被 kill（rc=124，尾部还有 `failed to get subscription count: publisher's context is invalid`），
  导致 `/api/servo` HTTP 请求超时。
- **根因**：`ros2 topic pub` **默认等待至少 1 个订阅者**才发布；`--once` 只是"发一条即退"，**并不取消等订阅者**。

- **对策**：自写 `webui/servo_pub.py`（rclpy 发布者 + **有界 3s** 等订阅者）：有订阅者发布并 rc=0；
  无订阅者 rc=3 并明确报"无 /servo/cmd 订阅者"，HTTP 立即返回可读错误而非挂起。
- **通用教训**：任何在 HTTP/脚本里"发一条 ROS 消息"的场景，**别裸用 `ros2 topic pub --once`**——
  无订阅者即挂起；用有界等待并区分"发送成功/无接收者"。

### #45 图像话题 RELIABLE 背压 + 常驻探针订阅 → 相机 30Hz 被顶到 ~8Hz（2026-09-30，YOLO26 帧率优化时发现）
- **现象**：`camera_node` 单独跑只有 **6–9Hz**（文档/真值应 ~30Hz），而 `camera_node` CPU 仅 ~25%

  合计仅 21ms/帧 ⇒ 时间全耗在发布。
- **根因**：本包图像话题用 **RELIABLE + KEEP_LAST(1)**；当存在**未及时 ack 的订阅者**时，
  可靠发布端被重传/ack 拖住（把发布端"顶着走"到消费端速率）。
- **触发源（实测）**：常驻的 `webui/server.py` → `ros_probe.py` 订阅了 `/vision/color/image_raw`

    **精确停掉 webui 后**立即降到 **0.38ms**，`camera_node` 立刻回到 **29.97Hz**。
  - 与**可靠性/depth 无关**：BE/REL、depth1/10 对照都复现；**换新话题名则不复现**
    （即"该话题上已有订阅者"是关键，且与发布端 QoS 无关）。
- **对策**：
  1. **图像话题一律用 BEST_EFFORT**（ROS2 传感器流标准做法）——本节点已加参数
     `image_qos_reliable`（默认 true=原行为；false=BEST_EFFORT）；`camera_node` 与

  3. 认识 RELIABLE 的**自限速**副作用：相机被慢 detector"顶着"，端到端帧率≈消费端速率；

- **通用教训**：高频大消息（图像/点云）**不要用 RELIABLE + KEEP_LAST(1)**；这是端到端帧率的
  隐形天花板，且表现为"生产者 CPU 不高但就是慢"。

  单帧延迟由 kernel 启动/同步开销支配；CPU 16 线程本身已很强。
- **附带坑1（Ubuntu jammy 自带驱动太旧）**：`intel-opencl-icd 22.14`（2022）在 6.8 内核 +
  Raptor Lake 上 `clinfo` 返回 **0 platform**（ACL 权限没问题、库都在）。必须加 Intel 官方源升到 25.x。
- **附带坑2（Intel 源拆包）**：新源把 `libigc/libigdfcl` 拆成独立包 `libigc1/libigdfcl1`，
  单独装 `intel-level-zero-gpu` 会报 `libigc1>=1.0.12812 未满足`（旧 ICD 把版本钉死）。
  **正解：`intel-opencl-icd libigc1 libigdfcl1 libigdgmm12 intel-level-zero-gpu level-zero` 一起升级。**
- **附带坑3（batch 写死）**：导出模型的 attention 里 `Reshape` 常量把 batch 固定为 1
  （`[1,2,128,400]`），reshape 到 B=8 报 shape 不符 → **无法用 GPU 批吞吐补救**（需从 PyTorch 侧重导出）。
- **对策/结论**：本机维持 **CPU + NNCF INT8**（更简单、免 GPU 驱动依赖、功耗低）；iGPU 驱动留着备用。
- **通用教训**：**"有 GPU" ≠ "更快"**——小模型/单帧实时场景先实测再投入；iGPU 的甜点区是
  大 batch、多路、或大输入，而本模型因 batch 写死连大 batch 都做不了。

### #54 `readline() is not None` 把 stdin EOF 当"已按 Enter" → 无人值守自动起飞（2026-09-30，T2 回归探测实测飞了整段任务）

  1. **"只打印/干跑"的验证命令绝不能让被测脚本保留起飞能力**——先用 EOF/超时负例堵死授权再跑；
  2. `timeout` 杀节点与 FAILSAFE 的 RTL 有竞态：context 被关后 set_mode 客户端不可用 → **空中被 SIGTERM 时 RTL 可能发不出**，无人值守飞行必须有外部看门狗兜底 RTL/LAND；
  3. 同工作区 `semi_auto_drop_test.py` 用的是正确写法（`bool(stream.readline())`）——移植时"对照相邻脚本"能提前发现（#20 同款）。

### #55 `pgrep -f "<含目标的命令串>"` 把运行命令的 shell 自己也匹配上 → kill 自杀（2026-09-30，配 Clash 自启动时踩出）
- **现象**：一条 `OLD=$(pgrep -f "clash -d /home/lab/clash"); [ -n "$OLD" ] && kill $OLD` 跑下去，输出在 `kill` 处**戛然而止**——不是 clash 没死，而是**执行这条命令的 bash 把自己杀了**（它的 cmdline 里正好含这个字符串），后续 `systemctl enable` 等步骤全部没跑。
- **根因**：`pgrep -f` 匹配的是**整条命令行**，不是"某个可执行文件"。凡是命令文本中含该模式的进程（当前 shell、`bash -c` 包装、编辑器、别的 ps/grep 管道）都会被列进去，`kill` 一视同仁。
- **对策**：不用 `pgrep -f` 找内核，改成两步——先按**进程名**精确定位，再读 `/proc/<pid>/cmdline` 确认是我们要的那个：
  ```bash
  clash_pids() {
      for p in $(pgrep -x clash 2>/dev/null); do
          tr '\0' ' ' < "/proc/$p/cmdline" 2>/dev/null | grep -q -- "-d $CLASH_DIR" && echo "$p"
      done
  }
  ```
- **教学**：与 #15（禁用 `pkill` 模糊杀）同源，但更隐蔽——`pkill` 至少名字就叫"模糊"。**"按模式找进程再 kill"必须两步走：精确定位（`-x` 进程名 / 端口归属 / systemd 单元）+ cmdline 复核；`pgrep -f | xargs kill` 迟早杀掉自己或邻居。**

### #56 桶尺寸比值必须先还原物理尺寸（2026-09-30）
- **现象**：旧逻辑使用 depth_m/识别框对角线像素；同一只桶距离变化时比值按距离平方变化，200mm 标定值无法跨距离复用。
