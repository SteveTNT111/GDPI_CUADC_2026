  ```
  等待本地位姿 ... → 本地位姿已就绪 (x=0.000 y=0.000 z=0.190)

  飞行模式切换至: LOITER
  流程完成：无人机已切换到 LOITER 模式保持悬停
  悬停监控中... mode=LOITER armed=True z=3.20 → 3.18 → 3.19 m（持续 34s+ 稳定）
  ```
  - 结果：**通过**（GUIDED 解锁 → 起飞到 3m → 切 LOITER → 稳定悬停）
- 关键技术点（翻译层）：
  - ROS2 的 `get_logger().info("fmt %s", arg)` 不支持 printf 多参数（会抛 `TypeError`），必须用 `"fmt %s" % arg` 拼接（第一次跑卡在"等待本地位姿"实为此 bug，非 QoS 问题）
  - 后台 `MultiThreadedExecutor.spin()` 线程驱动订阅回调（ROS2 的 `rate.sleep()` 不处理回调；ROS1 的 `rospy.Rate.sleep()` 会）
  - 删除 ROS1 的 roscore 自动启动逻辑（ROS2 无 master），保留 MAVROS 自动启动（`ros2 launch mavros apm.launch fcu_url:=...`）
  - 脚本参数名前缀 `~` 去除（`--ros-args -p takeoff_altitude:=3.0`）
  - 已确认：BEST_EFFORT 订阅对 /mavros/state（RELIABLE）与 /mavros/local_position/pose（BEST_EFFORT）均可收到数据
  - **图发现竞态修复**：`_ensure_mavros()` 原先直接用 `count_publishers("/mavros/state")`；ROS2 DDS 发现是异步的，新建节点后可能短暂返回 0 → 误判"MAVROS 未运行"并重复启动（两 MAVROS 抢 5760 → 连接超时）。已改为先给 `mavros_discovery_grace`（默认 3s）宽限窗口再判定（ROS1 经 master 同步，无此问题）
  - **退出崩溃修复**：`executor.shutdown()` 后先 `spin_thread.join()`，再 `destroy_node()/rclpy.shutdown()`，消除 "terminate called without an active exception"
- 仿真层修复（非 A3 代码问题）：
  - **SITL 静默崩溃**：官方 `iris_with_ardupilot` 模型 `<lock_step>1</lock_step>` 在 MAVROS 负载下使 SITL 崩溃；工作区覆盖为 `<lock_step>0</lock_step>`（`models/iris_with_ardupilot/model.sdf`，经 `GZ_SIM_RESOURCE_PATH` 优先生效），实测稳定 15min+
  - **LOITER 掉高根因**：SITL（`--model JSON`）无真实 RC。`AP_RCProtocol_UDP` 收不到外部 RC 包时以 50Hz 合成默认值 `[1500,1500,1000,1500,1800,1000,1000,1800]`，油门 ch3 恒为 1000（最低位）。GUIDED 忽略油门故起飞正常；LOITER 用油门控制升降 → 持续下沉至地面（BIN 日志 CTUN.TAlt 平滑下坡、RCIN C3=1000）
  - **修复**：`scripts/sitl_rc_center.py` 向 SITL RC-in UDP 端口(5501)注入 `uint16[16]`（ch3=1500）；`scripts/sitl_rc_center.parm` 设 `PILOT_THR_BHV=1`（自回中油门）以跳过 "Throttle (RC3) is not neutral" 解锁检查、并使摇杆中位=悬停。`scripts/restart_sim.sh` 已自动集成
- 结果：**通过**（含 LOITER 稳定悬停）
- **2026-09-22 GUI 实况复验**：`gz sim -g` 图形界面 + SITL + MAVROS + RC 注入下，命令 `ros2 run cuadc_control one_key_takeoff.py --ros-args -p arm_settle_time:=5.0 -p auto_start_mavros:=false` 一键起飞 → armed=true、z=3.19m（目标 3.0m）、GUIDED→LOITER 悬停、速度 ~0.0002m/s、高度纹丝不动 3.190000057220459（3 次采样一致），用户屏幕实况确认。A3 节点退出后 LOITER 自主保持。
- **SITL 启动间歇崩溃（2026-09-22 排查）**：lock_step 修复后仍偶发 —— 重启后 MAVROS 刚连上的 ~60-90s 窗口内 SITL 无声死亡（5760 消失、日志停在首帧 JSON 处理处）；gdb/降速下不复发 → 纯时序竞态。对策：SITL 用 shell 后台方式拉起后先盯 90s 危险窗口，存活即稳定；另确认 `request_streams.py` 需链路健康时调用（SITL 活着才 8/8 成功），SR0_* 只是速率门控、不会主动推流。

## B1 — camera_node.py 相机节点（2026-09-22 ✅）

- 验证（SITL + GZ，`ros2 run cuadc_vision camera_node.py --ros-args -p source:=gazebo`）：
  - `/vision/color/image_raw`：`bgr8` 640×480 step=1920（921600 B）
  - `/vision/aligned_depth/image_raw`：`32FC1` 640×480 step=2560（1228800 B，单位米）
  - `/vision/color/camera_info`：`plumb_bob`，K=[462.3,0,320,0,462.3,240,0,0,1]，P 有效
  - 稳定发布 **~17.2 Hz**（= GZ 原始 17.1 Hz，零丢帧；传感器按 sim-time 30Hz 出图，受 RTF≈0.6 限制）
- 关键技术点：
  - **ros_gz_bridge 不可用**：`~/ros2_gz_ws/install` 下有 `ros_gz_bridge`/`ros_gz_sim` 残留，但只有 `share/` 无 `lib/` 可执行，`ros2 pkg list` 不识别 → 改用节点内 `gz.transport13` 桥接（`gz.msgs10.image_pb2.Image` / `camera_info_pb2.CameraInfo`），外部接口不变
  - **性能坑（重要）**：rclpy 的 `uint8[]` 字段底层是 `array.array('B')`，直接 `msg.data = <bytes>` 会走逐元素转换（921KB ≈ **52ms**），把发布率从 30Hz 拖到 **8Hz**，且额外 CPU 占用拉低 GZ 实时因子；改为 `msg.data = array.array('B', arr.tobytes())` 后回到 ~17Hz
  - **step bug 修复**：原 ROS1 版 `_make_img_msg` 用 `shape[1]*dtype.itemsize`，忽略通道数 → bgr8 会得到 step=640（应为 1920），`cv_bridge` 会误读；ROS2 版改用行字节步长 `arr.strides[0]`
  - ROS2 `sensor_msgs/CameraInfo` 字段为小写 `d/k/r/p`（ROS1 为大写 D/K/R/P）
  - GZ 像素格式映射：color `RGB_INT8`(3)→cv2 RGB2BGR→`bgr8`；depth `R_FLOAT32`(13)→`32FC1`；另兼容 `L_INT8`/`BGR_INT8`/`L_INT16`/`R_FLOAT16`
- 仿真层（非翻译问题）：相机加在 `models/iris_with_ardupilot/model.sdf`（`color_camera` + `depth_camera`，640×480@30Hz，`always_on`）；headless 软件渲染下 RTF≈0.6，故 wall-clock ~17Hz。真机走 pyrealsense2 路径为 30Hz

  - `gz sim -g` 主窗口 `Gazebo Sim`（IsViewable、完整渲染赛场+无人机+Entity Tree）经 service 暂停/恢复实证**实时响应**（暂停按钮 ROI 像素差分 1.64%，stats `paused: true` 往返一致）；RTF 状态栏持续刷新。

### 关键结论（附实据）
1. **导航模式最大平飞速度 = `WP_SPD` = 10.0 m/s**。ArduCopter **4.7.1 已改 SI 命名**：`WPNAV_SPEED`(cm/s)→`WP_SPD`(m/s)、`WPNAV_SPEED_UP/DN`→`WP_SPD_UP/DN`、`WPNAV_ACCEL`→`WP_ACC`、`WPNAV_RADIUS`→`WP_RADIUS_M`、`LOIT_SPEED`→`LOIT_SPEED_MS`；`ANGLE_MAX`(cdeg)→`ATC_ANGLE_MAX`(deg)=30。本机**无 `WPNAV_*`/`SR*`/`AIRSPEED_*`**（Copter 无需空速）。判定以实际参数表为准（→错题本 #31 坑1）。
2. **MAV0 链路现状**：本固件无 `MAV_0_*`（点号变体），流率用 **`MAV1_*`/`MAV2_*`/`MAV3_*`**（1-based，MAV1↔SERIAL0/5760、MAV2↔SERIAL1/5762、MAV3↔SERIAL2/5763）；`SERIAL0_PROTOCOL=2`(MAVLink2)、`SERIAL0_BAUD=115`(→115200)。**30 个流率参数全为 0**，故新连接必须 `SET_MESSAGE_INTERVAL` 才推流（#2）；`MAVn_*` 参数 `@RebootRequired`，改动需重启 FC 才生效（实测：清空覆盖后单写 `MAV3_POSITION=10` 无任何消息）。
3. **坐标频率**：墙钟不达标**纯属仿真环境** —— Gazebo **RTF≈0.25**（相机传感器在 server 渲染 + GUI），飞控消息按 sim-time 调度，`墙钟频率 = 配置频率 × RTF`。**÷RTF 归一化后 11.95/10.08/8.57/9.66 Hz（逐话题前后采样 RTF 取均值）全部 ≥ 要求**，说明 FC 侧流率请求正确；真机 RTF=1 可达标。真机目标值（MAVROS 链路 MAV1）：`MAV1_POSITION≥10`、`MAV1_EXTRA1≥10`、`MAV1_EXT_STAT≥5`（改后重启）。**POSITION 组同时含 ID32/ID33；EXTRA1 含 ID30（ID31 需单独请求）；EXT_STAT 含 ID24**（源码 `GCS_MAVLink_Parameters.cpp` 实据）。

5. **工具可重复跑**：连跑多遍均 1389 参、同样的 PASS/FAIL 结构；`interval_test` 劣化（1Hz→~0.25Hz）与恢复（10Hz→~2.5Hz）证明 PASS/FAIL 判据对"配置流率"敏感，本次 FAIL 只由 RTF 引起。

## 修复：冷启动时"自动拉起识别"漏拉相机 → 视觉依赖 30s 超时（2026-09-30，错题 #60）

### 背景（用户实测反馈）
用户勾选 `auto_start_detector=true` 后跑全自动任务，日志显示**识别起来了但相机没起**，随后
`等待 camera/detector/aim_info 就绪...` → `视觉依赖未在 30.0s 内就绪` → `FAILSAFE`，任务失败。

### 根因（代码 + 日志双向印证）
- `auto_drop_test.py` `start_dependencies` 旧写法的启动分支是**互斥**的：
  `if not detector_running: spawn(识别) elif not camera_running: spawn(相机)`。
  **冷启动（识别也没跑）命中第一分支 → `elif` 永不执行 → 相机从不启动**。
- 而 `_detector_launch_command()` 对 Y26 显式传 `auto_start_camera:=false`（"相机由脚本单独管理"），
  故没有任何进程启动相机。就绪判据要求 `camera_node + detector_node + aim_info` 三者齐 → 必超时。
- 用户日志侧：有识别启动/加载行，**无相机启动行**；结尾 `视觉依赖未在 30.0s 内就绪`。

### 改动（最小）
`src/cuadc_control/scripts/auto_drop_test.py`：把互斥 `if/elif` 改为**两条独立 `if`**——
识别没跑就拉识别、相机没跑就拉相机，互不遮蔽；两者都在跑时仅打"不重复启动"日志。

### 实据
- `python3 -m py_compile src/cuadc_control/scripts/auto_drop_test.py` → OK；
  `colcon build --packages-select cuadc_control` → `1 package finished`，`install/` 内副本已含新逻辑。
- 控制流复刻（old/new 四态）：
  ```
  状态           旧逻辑                  新逻辑
  冷启动(都没跑)   spawn_detector          spawn_detector+spawn_camera
  只有识别         spawn_camera            spawn_camera
  只有相机         spawn_detector          spawn_detector
  都在跑           none                    none
  冷启动修复断言： PASS
  ```
- **端到端冷启动飞行验证未做**：当前环境已有遗留 `camera_node`(pid 1772029) 与停在"按回车关闭窗口"的启动器
  (pid 1861529)，非干净冷启动，且避免打扰用户在线环境 → 留待下次干净冷启动实跑确认。

### 边界 / 教学
- 该 bug 只在"识别与相机**都**未运行"的冷启动路径触发；若相机已在跑（如 WebUI「一键启动依赖」先起过），
  旧代码也能工作——所以此前未暴露。
- 多依赖"各自可能缺失"时用**独立 `if`**，不要用 `elif`；配置文案（"相机+识别"）与实现不一致时以代码为准。
